## 1. Question

the 64-case held-out cohort (burgers2d-speed hold64 jobs 4242040 / 4242063 / 4242036 at $256^2$ / $512^2$ / $1024^2$;

## 3. Cohort, reference, error

- Test cohort **test64 = hold64** = `params_draw(20260916, 64)`, physical sha256 `cd058fd2…` (gated). These 64 cases
  have never been used to fit, choose or tune anything; they were opened before only by the earlier held-out jobs
  listed in §1, which measured fixed settings.
- Reference `fft_tight` (Newton, ntol $10^{-6}$) on the same mesh.
- Error of an arm = worst over the 64 cases of the max over the five evolved output times of
  $\lVert u-u_{\rm ref}\rVert/\lVert u_0\rVert$ (percent); the median over cases is reported beside it.

## 4. Timing and the FOM rule (as the parent held-out jobs)

- Driver `b2test.py` = `burgers2d-speed/b2speed.py` @ `fb4a9ff7` + C4 (`bank_columns`, verbatim from
  `burgers-eq-tol-knobs/eqtol.py`, used at $4096^2$ only).
- A–B–A: warm-up of every subject; ROM phase A1 (2 reps × 64 cases, order randomised within a case), FOM phase B
  (1 rep × 64), ROM phase A2 (= A1); 5 s cool-down + 2 s dummy kernel between phases; burn 0.1 s before every
  invocation (0.25 s at $4096^2$, as bk4096b / e4096c); `block_until_ready` on both sides; GPU time = dense input
  resident on the GPU → six dense output fields. Arm time = median over A1 ∪ A2 invocations; FOM time = median over B.
- FOM grid: the 15 Newton–BiCGStab settings of the parent lanes, in **both** compile modes at $256^2$–$2048^2$ (as
  h256/h512/h1024), default only at $4096^2$ (as bkh64f/bk4096b). At $4096^2$ four settings are not timed —
  `fft_tight`, `lean_tight`, `nt1e-4_dt005`, `lean_nt1e-4_dt005` — the slowest of the dev grid (≥ 2.3× the dev
  Table-1 comparator's time); they are scored, so they are still eligible for the error condition, but can never be the
  comparator (bkh64f untimed three of them for the same reason).
- **Table-1 FOM rule (one FOM per mesh):** the fastest timed (setting, mode) with `nonlinear_converged` on every case
  whose worst evolved error is ≤ the **accurate** arm's worst error **on these test cases**, in this job. Speedup of
  every arm = that FOM's median ms / the arm's median ms, both from the same job. Each arm's own comparator (fastest
  FOM at least as accurate as the arm) is reported beside it.
- GPU: A100 80 GB at every mesh (4096²: `bank_columns = 384`, `bank_blocks = 24`, memory fraction 0.95, as e4096c).
  Absolute ms are A100; only same-job ratios are compared with other jobs.

## 6. Integrity rules

- No setting, width, code path, compile mode, FOM grid, rule or gate is changed after a test number is seen.
- An improvement may be tried only if selected on the dev6 or validation cases, frozen here as a dated amendment, and
  then evaluated on the test cases once. **Every** test evaluation run is reported, including worse ones.
- An infrastructure failure (exit 42, node fault, disk full, OOM, pre-start cancellation) may be resubmitted once as a
  new attempt directory; a code bug found after submission is fixed, committed and resubmitted as a new attempt; both
  recorded here and in the lab log.
- The report is generated from the audited summaries by `reports/make_report.py`; the sha256 of every summary and
  `result.json` is recorded. No number is typed by hand.
