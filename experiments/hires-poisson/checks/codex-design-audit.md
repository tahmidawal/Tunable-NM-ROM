# Codex design audit — hires-poisson (2026-09-20, before the first GPU job)

Codex CLI 0.155.1, model gpt-6-astra, `--sandbox read-only`. First attempt could not read files (bubblewrap: `loopback: Failed RTM_NEWADDR`), so the second attempt inlined DESIGN.md, hp_core.py, hp_solve.py, hp_audit_np.py, config-2048.json and the four parent modules into the prompt. Verbatim final answer below; dispositions are DESIGN.md amendment A1.

**Do not launch yet:** the audit can report success despite failed gates, and the configured f32 tolerance contradicts the design.

1. **Critical — gates do not control acceptance.** `hp_audit_np.main` hardcodes `passed=True`; failed parity, stationarity, CG convergence, and nondeterminism merely become report fields. `hp_solve.main` likewise writes `COMPLETE` regardless. Empty parity/diagnostic lists pass `all(...)` vacuously. Assert required coverage and gate results before declaring success or deleting fields. The audit trusts `matches_saved_field` rather than independently requiring every invocation hash to equal the saved field’s hash; mismatched rows escape error verification.

2. **High — f32 configuration contradicts preregistration.** `config-2048.json` specifies `parity.f32_field=1e-5`, whereas `DESIGN.md` explicitly adopts `1e-4` after observing approximately `4e-5` for the linear rung. Reconcile these before launch; the current configuration retains the previously failed threshold.

3. **High — matched-accuracy selection and verdict are missing.** Despite its docstring, `hp_audit_np.main` computes neither matched selections, speedups, nor the protocol verdict. Selecting the fastest arm by worst physical error is sound **on an identical cohort**. A restricted CG arm cannot compete using its smaller-cohort maximum or timing median against twelve-case ROM summaries. Require common cases, declared repetition counts, valid solves, and an explicit “no eligible comparator” result. Currently even missing subjects/cases are not rejected.

4. **High — parity is narrower than claimed.** `hp_core.make_lean` uses the same projection, projected nearest-code selection, LM settings, and triangular recovery as `correction_core.prepare_correction.kernel`; mathematically it is the same query. Floating-point identity still needs measurement. However, retained and lean share the **new** assembled `B`, so their parity cannot detect assembly errors relative to `core.assemble`. Add an independent small-mesh assembly comparison. With only lean32, parity is skipped entirely; no code verifies the promised same-commit 2048 carryover. The linear f64 rung also lacks an independent baseline.

5. **High — validation was removed, not fully relocated.** `hp_core.make_diagnose` restores stationarity but omits correction-recovery backward error, residual reconstruction, and projected-Jacobian rank from the retained kernel. Recorded LM backward error is not gated. `hp_solve.main` diagnoses only the first precision variant. `make_linear` reports condition number without checking rank or solve validity. Restore applicable checks; validate the actual rounded decode separately where relevant.

6. **Medium — assembly and floor are algebraically correct, with numerical caveats.** `build_bank.contract` computes the required normalized sine contraction; `make_ops` gathers identical mode indices and correctly applies inverse eigenvalues only to the source. Stacked chunk QR preserves \(G^\top G=R_g^\top R_g\). Consequently, `solve_triangular(Rg.T, gtu.T)` gives projection coordinates and the stated floor formula is correct. Subtracting nearly equal squared norms can lose accuracy; clipping negative values can conceal failure. Check cancellation/conditioning and independently evaluate projection residuals on a small mesh.

7. **Medium — timing scope matches, diagnostic costs do not.** `lean_query`, `linear_query`, `generic_query`, and `correction_query` all charge full f64 source upload and full f64 field download. Coarse subsampling and interpolation are charged. However, `iterative_core.make_cg` charges an additional true-residual stencil/norm while lean stationarity is untimed; this biases speedup toward lean, especially for cheap coarse solves. Report or harmonize diagnostic scope. Setup is excluded, so claims concern amortized queries. Point sampling plus bilinear interpolation is a fair declared control for these smooth sources, though not an exhaustive best coarse solver.

8. **Medium — memory needs explicit headroom.** At 2048, f64 chunks, f32 chunks, and retained concatenation occupy approximately **42.9 GB**, plausibly fitting 141 GB with workspace. At 4096 the same combination needs **171.7 GB**, impossible. Without retained, both precisions still consume approximately **103 GB** before feature activations, QR workspaces, references, and allocator overhead. A 256-row f64 chunk alone is approximately **4.3 GB**. `G.block_until_ready()` does not synchronize all downstream consumers; bound in-flight work before relying on chunking to cap peak memory.
