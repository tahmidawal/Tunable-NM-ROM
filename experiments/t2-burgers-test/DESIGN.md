## 3. Timing and the Table 2 FOM rule (the source driver's protocol, unchanged)

- Driver `tcmp.py` = `burgers-compare-hires/cmp.py` @ `07c0e3e8` + the changes in §4. Phase F: the 15 Newton–BiCGStab
  settings and the head arm in one randomised order (order seed 20260923), 5 repetitions × 64 cases, burn-in 0.25 s
  before every invocation. Phase S: the span arm in its own block (5 × 64, burn-in before each), after its held-out
  rho check. Phase B: bracket re-timing of every Phase F subject (2 × 64) for the drift gate. GPU time = supplied dense
  initial field resident on the GPU → six dense output fields, `block_until_ready`. Arm time = median over its timed
  invocations.
- Operators: `ops/optime.py` (source copy + §4 changes) in the same allocation after the JAX phase, 20 burn-in + 5
  timed repetitions per case, device time from on-device input to on-device trajectory.
- **Table 2 FOM rule (one FOM per cell):** the fastest (Phase F median GPU ms) of the 15 settings whose worst evolved
  error on these 64 test cases is $\le$ the worst error of the **accurate** arm (`bank384…`) in this job. Every row's
  speedup = that FOM's median ms / the row's median ms, same job. Each row's own comparator (fastest FOM at least as
  accurate as the row) is reported beside it.
- GPU: 256² and 1024² on A100 80 GB (as opt201 / p1024), 2048² on H200 (as p2048e). Absolute ms are never compared
  across jobs; only same-job ratios.

## 4. Changes against the source driver (all declared; none depends on test results)

1. Cohort = test64 (§2.3) instead of dev6; extra disjointness assertions.
2. Arms reduced to the two Table 2 NM-ROM settings. Not run: $q=256$ (reference-only rows), the robust-rule arm,
   bank-span $R'\in\{512,256,128\}$ and `lat128`, POD-LSPG, the quadratic manifold (none is in Table 2). This removes
   the $q=256$ lat64 arm from the Phase F randomised mix, so the Phase F subject set is 15 FOM settings + 1 ROM arm
   (was + 2).
3. Field storage: at 64 cases full fields for every (arm, case) do not fit (≈300 GB at 2048²). Full fields are kept for
   case 0 only; every case keeps a 65×65 sub-grid (every $L/64$-th node) field. In-job errors are full-grid; the
   NumPy audit (`t2audit.py`) recomputes case 0 on the full grid and every case on the sub-grid and must match the job
   to $10^{-9}$ relative. Operators' full-grid errors are computed in `optime.py` against the same in-job truth.
4. Operator cohort files are written for the test split and deleted after the operator phase (disk).

**Deviation D1 (256²).** The Table 2 256² cell came from a different driver (ops-timing-panel `panel.py`, opt201,
job 4181372), with the head arm `q0_M64_eqcert_g1em06_fastL4` (1.8891 % dev), an 8-setting non-lean FOM grid and a
4096² discretisation reference. That driver's 4096² reference for 64 cases does not fit the cutoff, so the 256² test
cell uses **this** driver (same arms as 1024²/2048²; head arm = the `eqtop`-rule $g=10^{-3}$ arm, which scored
1.8898 % on dev6 in opt201). To give a like-for-like development value, attempt `d256` runs the identical 256² job on
dev6. The 256² row reports both FOM rules: the full 15-setting grid (primary, as 1024²/2048²) and the non-lean
`b_panel` subset (the grid of the dev cell).
