# Making the ROM rollout 2.2× faster at bit-level parity: diagnosis, the optimization ladder, and the A100 confirmation

Follow-up to `2026-08-27-b1d-scaling-and-fom-cost.md`, user-directed ("why is
our ROM so slow, is it utilizing the GPU properly, optimize it, iterate,
keep the same error"). An autonomous optimization pass (full experiment log:
`experiments/separable-decoder/OPTIM-NOTES.md` on branch
`exp/2026-08-27-b1d-poissonqf`) followed by an A100 confirmation (jobs
2976993/2976994). Numbers **final**; every kept change is a pure
implementation change verified to leave the solver's arithmetic path intact
(errors match the committed baselines to $\sim 10^{-9}$ relative, stop-reason
histograms identical). Tables T-O1/T-O2 generated by
`gen_2026-08-27-b1d-nodes-and-poisson-qf.py`.

## Why it was slow (the diagnosis, measured)

The rollout is one compiled GPU program (50 time steps, a damped LM loop
inside each), but each LM iteration moves only ~0.1 MFLOP through 10–15
micro-kernels — the program is **kernel-count bound**, not compute or
occupancy bound. The reported "86% SM utilization" is misleading on that
counter (it measures any-kernel-resident time, not useful occupancy). The
decisive measurement: the $(8{\times}8)$ normal-equation solve through
cuSOLVER cost **~110 µs of every ~120 µs LM iteration** — roughly 45% of
the whole solve — because a general LU factorization call is absurd
overkill for an 8-unknown system. This matches the project's 2D Round-4
profiling (dispatch-bound, ~0.14 ms/iteration) exactly.

## What was changed (kept) and what was tried and rejected

**Kept — all pure implementation, parity-verified:**
1. The cuSOLVER solve replaced by a **broadcast Gauss–Jordan elimination**
   written in plain array ops (~28 µs vs ~110; f64 agreement with LU
   $4\times10^{-16}$).
2. Residual and Jacobian computed in **one pass** (`jax.linearize`), the
   `lax.cond` removed from the loop body.
3. **Per-trajectory constants hoisted**: the mode weights and every matrix
   they multiply are constant for a whole trajectory (fixed viscosity) and
   are now folded once per rollout instead of recomputed every residual
   call; the decoder head's last layer is merged with its linear skip; the
   exact-linear projection and node features contract in one matmul.
4. Small matvecs done as broadcast-reductions (no cuBLAS calls), outer
   scan unrolled 5×.

**Tried and rejected, with numbers in OPTIM-NOTES.md:** a scalar-unrolled
Cholesky (slower — long serial fusion chains), XLA command buffers / CUDA
graphs (zero effect on the rollout), masked inner-loop unrolling (slower),
and a reduced-init IC fit — rejected on **parity evidence**: the IC
landscape is multimodal (the mean-code init alone lands 30–80% worse on
5/8 trajectories), so cutting inits is an algorithmic change and stays out.
Iteration capping and tolerance loosening were forbidden from the start
(the 2D campaign measured capping collapsing error to 0.6–0.8).

## The A100 confirmation

Reference and optimized paths ran interleaved in the same job on the same
GPU, loading the *committed* checkpoints and node sets (nothing retrained),
with parity checked against the committed baseline JSONs in-job.

- **Speed: 2.20–2.25× end-to-end on every sampled arm at both N=512 and
  N=4096** (IC fit 16.6→8.0 ms, latent solve 34.5→15.0 ms; oracle arm
  1.9×). Flat in N, as before.
- **Error: unchanged to $\le 5\times10^{-9}$ relative** against the
  committed baselines, identical stop-reason distributions, latent-path
  deviations $\le 2.4\times10^{-8}$ — the solver takes the same steps.
- **Against the FOM:** single-query, the gap narrows from 5–8× slower to
  **2.5–3.0× slower** (ROM 22–24 ms vs FOM 8–9 ms). The **amortized
  throughput arm** (the identical rollout vmapped over the 8 test
  trajectories, values bit-identical) reaches **7.9 ms/trajectory at
  N=512 and 6.6 ms at N=4096 — at or below the FOM's single-query cost.**
  Honesty labels: that is throughput, not latency; a vmapped while-loop
  pays each batch's worst-case iterations; and the FOM was *not* batched
  for comparison, so no "ROM beats FOM" claim is made — the supportable
  sentence is "for many-query workloads the optimized ROM's per-trajectory
  cost is in the FOM's single-query range."

## What carries beyond 1D

The kept optimizations are not 1D-specific: the tiny-system Gauss–Jordan
solve, one-pass residual+Jacobian, per-trajectory constant hoisting, and
cuBLAS-free small matvecs apply verbatim to the 2D exlin rollout (K=16–32,
the same LM loop, the same per-iteration kernel anatomy the 2D Round-4
profiling measured). Porting them to `sep_burgers_exlin.py`'s solve path is
the obvious next lever on the 2D paired speedups (1.87–1.90× today) — not
done here, listed as open.

## Glossary

- **Parity** — the requirement that an optimization change *what is
  computed* not at all: same rollout errors (to ~1e-9, far inside seed
  noise), same accept/reject/stop decisions at every LM iteration, same
  latents along the path. Anything failing parity was rejected even if
  faster.
- **Kernel-count bound** — wall time set by the number of GPU operations
  launched, not by arithmetic: each operation is microseconds, and the gaps
  between them dominate.
- **cuSOLVER / cuBLAS** — NVIDIA's factorization and matrix libraries;
  built for large matrices, their fixed per-call overhead dwarfs the actual
  work for 8×8 systems.
- **Gauss–Jordan (broadcast)** — solving the 8×8 system by elimination
  written as a handful of fused array operations instead of a library call.
- **Hoisting** — moving computations that cannot change during a rollout
  (everything depending only on the trajectory's viscosity) out of the
  per-iteration loop, done once instead of thousands of times.
- **Throughput arm** — running 8 trajectories simultaneously in one
  program; the per-trajectory cost is total time divided by 8. Fair for
  "many queries" workloads, not a latency figure, and the FOM was not
  given the same treatment.
