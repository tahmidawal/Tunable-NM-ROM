# A code-only GitHub mirror for this repository — plan, measured, awaiting approval

This report covers how to get this repository's **code, reports, audited result JSONs and
archive manifests** onto GitHub, given that its raw run archives cannot go there at all. Its
numbers are **final for the current state of the repository** — every one was measured on
2026-09-16 by `reports/generate_mirror_plan.py`, and the filtering was dry-run end to end into
a throwaway clone under a session scratchpad. **Nothing has been pushed, and no ref, object or
note in the working repository was created, moved or deleted.** The user's approval is the
next step; the exact command is in §6.

---

## 1. The problem, stated precisely

The working repository holds 212 GiB of Git objects. That is not a packing inefficiency: it is
raw experimental output that was deliberately committed, as bounded chunks, so that every
audited result would remain reproducible after the cluster job directories were deleted.

Three separate limits bite, and only the third is fatal:

1. **Repacking cost on the shared box.** A plain `git push` runs `git pack-objects` over the
   whole reachable set and reaches roughly 48 GB resident on the GB10, which `earlyoom` would
   answer by killing other agents' work. The 2026-09-15 session killed such a push
   deliberately.
2. **GitHub's per-file limits.** 50 MB is a warning, 100 MB is a hard rejection. Many
   individual chunk files are 64–90 MiB and some `.npz` fields exceed 1 GiB.
3. **GitHub's per-push pack limit, about 2 GB — and this one cannot be worked around.** A
   staged push can split a *branch* into several pushes, but it cannot split a *commit*. Seven
   commits on the consolidated lineage each introduce more than 2 GiB of new blob bytes in one
   commit (§3). **No branch descending from any of them can reach GitHub as-is**, no matter how
   the push is staged. The 2026-09-15 attempt got 375 of 416 commits across and then stopped
   exactly here.

A correction to the lab log while we are here: the 2026-09-15 entry named **four** such
commits. The measurement below finds **seven**. The four named are all present; three more
(`5974d3e0`, `1f576c9e`, `98917547`) were not listed, and one of them is the largest of the
set at 11.22 GiB.

## 2. The proposal

Publish a **separate, code-only mirror repository** whose history is this repository's history
with every raw archive path removed. Concretely:

- Every path matching one rule (§3) is deleted from **every commit** on **every ref**.
- Everything else survives: source, reports, `DESIGN.md`s, `LAB-LOG.md`, figures, and — this
  is the point — **every `result.json`, every `audit.json`, and every SHA256 manifest**. A
  reader of the mirror can still see exactly which archive belonged where, how many bytes it
  was, and what its hash is; they simply cannot download it from GitHub.
- The working repository is untouched and remains the archive of record. The mirror is a
  publication, not a migration.

**What this costs.** The mirror's commit hashes differ from the working repository's, because
the trees differ. The mirror is therefore a separate published lineage and cannot be pulled
back into the working repository. That is acceptable for a publication mirror and is the
reason this needs approval rather than being done quietly.

**What it does not cost.** No history is lost anywhere. Nothing is deleted from the working
repository. No archive is destroyed. The rule is reversible in the sense that the mirror can
be rebuilt from scratch at any time by rerunning one script.

## 3. Exactly what would be dropped

The rule, applied to the path of every blob in every commit:

```
(\.part-?[0-9]+$)|(/archive-parts/part-?[0-9]+$)|(\.(npz|npy|pkl|pt|pth|h5|hdf5)$)|(\.(tar|tgz|zip)$)|(\.tar\.gz$)|(\.gz$)
```

It is anchored on the basename, so a manifest sitting *beside* a chunk directory — a
`MANIFEST.sha256`, an `ARCHIVE.json` listing every part with its SHA256 and byte count — is
kept. The rule is a **path** rule, not a size threshold, because a size threshold would be
unstable: it would drop a large audited `result.json` on one branch and keep the same file on
another. The measured size distribution justifies the path rule: after applying it, **no
surviving file is anywhere near GitHub's 50 MB warning**, so no size rule is needed at all.

## 4. How the archives are referenced instead

Nothing is silently deleted. For every emptied directory the mirror retains the manifests that
already sit beside it, which the cells wrote at collection time. A representative example,
`experiments/mr-heat2d/runs/accuracy10/` — the largest single drop at 11.204 GiB:

| kept file | what it records |
|---|---|
| `ARCHIVE.json` | the cluster job id, the exact remote directory, the joined archive's SHA256, its total byte count, and for each of the 128 parts its path, byte count and SHA256 |
| `COLLECTION-CHECK.json`, `RETENTION.json`, `REMOTE-CLEANUP.json` | that the pull was checksum-verified, what was retained, and that the remote directory was removed |
| `archive/outputs/results.json` | the audited result itself, 15.05 MiB of it, which is what the reports are generated from |
| `audit.log`, `audit-final.log`, `collection.log` | the independent audit trail |

The newer cells use the same shape under a different name: `SHA256SUMS`,
`MANIFEST.sha256`, `OUTPUTS.sha256`, `PROVENANCE.json`, `archive.json`, `result.json`,
`audit.json`, `run.sbatch`, `COMMIT.txt`. All of these survive the filter. A mirror reader can
verify any archive they are given out of band, byte for byte, against the manifest in the
mirror.

What they cannot do is fetch the archive from GitHub. The recommended wording for the mirror's
`README` is a short note at the repository root — added as one commit on top of each mirrored
branch, so the filter itself stays a pure deletion:

> Raw run archives (chunked tarballs, saved field arrays, checkpoints) are not mirrored here;
> they exceed GitHub's per-push limits. Each archive's directory retains its manifest
> (`ARCHIVE.json` / `archive.json` / `SHA256SUMS`) giving every part's byte count and SHA256,
> and its audited `result.json`. The archives themselves live in the working repository.

## 5. Tooling, and why not `git filter-repo`

`git filter-repo` is **not installed** on this box (`git filter-repo --version` →
`'filter-repo' is not a git command`), and nothing was installed to make it available. The
script therefore uses `git filter-branch --index-filter`, which is available and — crucially
for this repository — operates on the **index** alone: it never reads, decompresses or writes
the multi-gigabyte blob contents, so the rewrite touched none of the 214 GiB.

If the user prefers `filter-repo`, it is a single dependency-free Python file and would install
into the local venv without touching the system:

```bash
/home/tahmid/Dev/.venv/bin/pip install --no-deps git-filter-repo
/home/tahmid/Dev/.venv/bin/python -c "import jax; print(jax.__version__, jax.devices())"   # must still print 0.10.1 [CudaDevice(id=0)]
```

It would produce the same mirror in one pass instead of one subprocess per commit. **It was
not installed, because installing into the shared venv is the user's call.**

The script is `tools/mirror-code-only.sh`. Its safety contract, enforced by construction:

- the source repository is opened read-only; no ref, note, reflog or object in it is written;
- the clone is made with `--shared`, so **no object is copied** and `git repack` never runs
  against the working repository — the 48 GB resident spike cannot happen;
- `refs/original/*` and the reflog are expired inside the throwaway only;
- the script **prints the push command and stops**. It never pushes.

## 7. The alternatives, and why this one

| option | verdict |
|---|---|
| Plain staged push of the real branches | **Impossible.** Seven single commits exceed the per-push pack limit and a commit cannot be split. This is what the 2026-09-15 attempt hit. |
| Git LFS for `*.part*` | Possible but expensive: 214 GiB against GitHub's LFS quotas, and every clone of the mirror would still have to be told to skip the LFS objects. It also does not solve the per-file 100 MB question for the largest `.npz`. Worth revisiting only if the archives genuinely must be downloadable. |
| History rewrite of the working repository itself | **Rejected.** It would invalidate every commit hash recorded in `LAB-LOG.md` and in every report, which is the one thing this project cannot afford. |
| **Code-only mirror (this plan)** | 170 MiB, one push, no installation, working repository untouched, every manifest and audited JSON preserved. |

## 9. Glossary

- **Blob / tree / commit / object** — Git's four storage units: a file's contents; a directory
  listing; a snapshot pointing at a tree plus its parents; any of these.
- **Pack / pack size / repack** — Git's compressed bundle of many objects; its size, which is
  what a push actually transfers; the operation that rebuilds it, and the operation whose
  memory use makes a plain push dangerous here.
- **Reachable** — an object that some ref can reach by following commits and trees. Unreachable
  objects are not pushed and are eventually garbage-collected.
- **Ref / branch / `--all` / `refs/original`** — a named pointer to a commit; the usual kind of
  ref; every ref in the repository; the backup refs `git filter-branch` leaves behind, deleted
  inside the throwaway only.
- **`--shared` clone / alternates** — a clone that borrows the original's object store instead
  of copying it, via a file called `objects/info/alternates`. It is instant and costs no disk,
  and it is why this dry run was cheap.
- **`--index-filter`** — a `git filter-branch` mode that rewrites each commit by editing its
  *index* (the list of paths and blob hashes) rather than checking the files out. It never
  reads file contents, which is why it can rewrite a 212 GiB repository in minutes.
- **`--prune-empty`** — drop commits that become empty once the filter has removed everything
  they changed. 47 of this repository's commits are exactly that: pure archive commits.
- **Chunked archive / `*.part0000` / manifest** — a large tarball split into fixed-size pieces
  so each fits Git's practical per-file range; one such piece; the JSON or text file recording
  every piece's byte count and SHA256 so the whole can be verified and rejoined.
- **`result.json` / `audit.json`** — the run's own recorded numbers, and the independent
  recomputation of them. Every report in this project is generated from these two, which is why
  keeping them is the whole point of the mirror.
- **SHA256** — the content hash used throughout this project to pin exactly which file was
  used. Kept for every dropped archive.
- **GiB vs GB** — $2^{30}$ bytes versus $10^9$ bytes; GitHub states its limits in GB and MB,
  Git reports in GiB and MiB, and both are used here as measured.
- **LFS (Large File Storage)** — GitHub's out-of-band store for big files, which replaces them
  in the repository with pointers. Considered and not chosen (§7).
