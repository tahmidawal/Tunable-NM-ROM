# JCP lane-agent rules (2026-10-08)

These are the operating rules every subagent follows when it runs a JCP campaign lane. They condense the repository's `CLAUDE.md` (the copy on `main` is authoritative and supersedes any older copy inside a worktree), the plan `reports/2026-10-06-jcp-offmesh-paper-plan.md`, and lessons learned. Status: in force from 2026-10-08.

## Where you may write
- **Only inside your own worktree** (`worktrees/<your-lane>/`), mostly under `experiments/jcp-<lane>/`. Never write to `main`, to another worktree, to `LAB-LOG.md` or to `notebook/`; the coordinator owns those. You may *read* anything.
- Commit small and often. After **every** commit run `bash experiments/jcp-<lane>/sync_github.sh`. Never `git push` an `exp/...` branch directly. Files over 50 MB are not mirrored: list them by SHA256 in a committed manifest.
- `vendor/` holds byte-identical copies of the off-mesh code (`vendor/PROVENANCE.json`). Do not edit them; copy into the lane directory before changing anything.

## Codex adversarial verification gates EVERY step (user instruction, 2026-10-08)
Before you act on anything, an independent Codex adversarial agent must check it. Use `codex exec -C <worktree> -o <lane>/audits/codex-<step>-<n>.md "<prompt>" < /dev/null`. The prompt must ask Codex to *try to break* the item and to give a per-item verdict of CORRECT / WRONG / NEEDS-RESTATEMENT. Read the output yourself; Codex's report is a claim to check, not a result. Fix every WRONG and re-run the audit until it is clean, then proceed. The gated steps are:
- the design (`DESIGN.md`) and each amendment;
- every code file, before it runs at real size;
- every cluster job, before submitting it: the config, the sbatch script, and that the outputs will answer the pre-registered question;
- every result, before it is reported: recompute and check the numbers against the raw outputs, and check that every control fired;
- the report and its plots, before you hand back.

Keep every audit file, committed in `audits/`. List them in the hand-back message, with their verdicts.

## The sequence (no skipping)
1. **`DESIGN.md` first** (pre-registration). It must state the question, the arms, the controls that must fail, the metrics, the pass/fail bars, the cohorts, the GPU-hour estimate and the deliverables. Use LaTeX for maths, and mermaid for any diagram.
2. **Codex design audit**, run before any code: `codex exec -C <worktree> -o <lane>/audits/codex-design.md "<adversarial prompt asking for a per-item CORRECT / WRONG / NEEDS-RESTATEMENT verdict>" < /dev/null`. The `< /dev/null` is mandatory. Do not pass `-s read-only`; put the guardrails in the prompt instead. Fix every WRONG, and append dated amendments to `DESIGN.md` (never rewrite history).
3. **Code, then a Codex code audit**, done the same way.
4. **A real-size smoke test.** Gates and controls must be checked at one real mesh before any verdict is read: a control that cannot fail on real data is a bug. Local GB10 runs must go through `jaxrun`, with **at most one local `jaxrun` per lane** (four lanes share three slots).
5. **Cluster jobs** (rules below).
6. **A Codex results audit**, then a report generated by a script in the lane (`experiments/jcp-<lane>/make_report.py` → `report.md`). **Never hand-type a number.** The report needs a level-1 title, a status line, LaTeX maths, and a closing plain-language glossary.

## Tufts cluster
- Use `ssh tufts-login`, the `gpu` partition only, and never `preempt`. Submit with `sbatch`. The pattern used by the 2026-10-01 lanes is in `vendor/quad2d/cluster/` and `vendor/quad3d/cluster/` (stage, submit, collect).
- **One job per directory**, under `/cluster/tufts/paralab/tawal01/<your-namespace>/<job>/`. Check `squeue -u tawal01` before and after every submit, and confirm exactly one job per directory.
- Inside every job:
  - activate `/cluster/tufts/paralab/tawal01/ae-research/venv`;
  - set `JAX_DEFAULT_MATMUL_PRECISION=highest` and use f64 where accuracy matters;
  - run the GPU preflight `python -c "import jax,sys; b=jax.default_backend(); print(f'jax_backend={b}'); sys.exit(0 if b=='gpu' else 42)"`; exit 42 means resubmit on another GPU type.
- Respect your lane's **concurrent-job cap**, given in your brief. Prefer A100/H100; use H200 for big 3D work.
- Pull results and logs back into the lane, then delete the cluster job directory. Treat an empty log as possibly disk-full.
- Record with every result: commit, config, seed, mesh, GPU, backend, precision, job id and output paths.

## Integrity
- **References are first-order today.** The second-order references lane has not run yet. Every accuracy comparison is therefore **provisional**; say so next to the number. Where the 2D space-only reference (S) is available, report it beside the space+time one (ST).
- **Cohorts:** select only on validation or development cohorts. Do **not** create or open any new sealed test cohort; that belongs to the references lane. The historical test cohorts (2D `test64`, 3D `923901`) may be reported for replication only, never used for selection.
- Timing: paired A–B–A runs inside one job on one GPU, with a warm JIT and a burn-in. Never compare times across GPU types.
- Never quote a pre-September Burgers speed-up. Never mention the heat POD-128 comparison.
- If something you find contradicts an earlier report, say so plainly; retractions matter more than successes.

## What to hand back
The final message to the coordinator must contain:
- what ran (job ids, GPUs, namespace);
- the key numbers, read from the generated report;
- what is provisional and why;
- anything wrong or retracted;
- the paths of the report, plots and DESIGN;
- the last lane commit and its mirror commit;
- open questions.

Make plots (PNG) for anything presentation-worthy: the coordinator will put them on the results page.
