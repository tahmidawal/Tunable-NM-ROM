# The separable decoder, and where Poisson stands

A short, plain-language picture of the model, plus every Poisson number measured so far.
Numbers are generated by `reports/gen_2026-08-25-poisson-summary.py` from committed run
JSONs — none are typed by hand. Poisson is the **control problem** in this project; the
harder target is Burgers (see `2026-08-25-burgers-h-generalisation-wall.md`).

---

## The model in one picture

The network answers one question: *given a point `x` and a 16-number code `z`, what is the
field value there?* It has two halves that never mix.

```
                      ┌───────────────────────────────────────────┐
    x = (x₁, x₂)  ──▶ │  SPATIAL TRACK   g(x)                     │
    a location        │                                           │
                      │   Fourier lift  [sin(2πBx), cos(2πBx)]    │
                      │            ↓                              │
                      │   small MLP   128 → 128                   │
                      │            ↓                              │
                      │   × bc(x) = 16·x₁(1−x₁)·x₂(1−x₂)          │ ← exactly 0 on the walls
                      └────────────────────┬──────────────────────┘
                                           │  512 numbers:
                                           │  "how dark is each sheet at x"
                                           ▼
                                    ⟨   ·   ,   ·   ⟩   ──▶   u(x; z)
                                           ▲
                                           │  512 numbers:
                                           │  "how much of each sheet to use"
                      ┌────────────────────┴──────────────────────┐
    z ∈ ℝ¹⁶       ──▶ │  LATENT TRACK   h(z)                      │
    the code          │                                           │
                      │   small MLP 128 → 128  +  a linear skip   │
                      └───────────────────────────────────────────┘
```

Read it as **512 transparent sheets**, each painted with a different ripple:

- `g(x)` says how dark each sheet is at the point `x`. **It never depends on `z`.**
- `h(z)` is the recipe: how much of each sheet to stack. **It never depends on `x`.**
- Multiply and add → the field value.

### The same thing with shapes and activations

Configuration below is the round-3/4 one: `n_ff=64`, `g_hidden=1024`, `R=512`, `K=16`.
Every hidden layer uses **SiLU** (`x·sigmoid(x)`); every output layer is **linear**.

```
   SPATIAL TRACK  g(x)                        LATENT TRACK  h(z)
   ═══════════════════                        ══════════════════

   x = (x₁, x₂)          (2,)                 z                    (16,)
        │                                          │
        │  x @ B     B:(2,64), trained             ├─────────────────┐
        ▼                                          │                 │
   ang                   (64,)                     │                 │ linear
        │                                          │                 │ skip
        │  [ sin(2π·ang) , cos(2π·ang) ]           │                 │ z·W
        ▼                                          │                 │ (16→512)
   Fourier features     (128,)                     │                 │
        │                                          │                 │
        │  W₁: 128→1024                            │  W₁: 16→128     │
        ▼  + b₁ , SiLU                             ▼  + b₁ , SiLU    │
                       (1024,)                                (128,) │
        │                                          │                 │
        │  W₂: 1024→1024                           │  W₂: 128→128    │
        ▼  + b₂ , SiLU                             ▼  + b₂ , SiLU    │
                       (1024,)                                (128,) │
        │                                          │                 │
        │  W₃: 1024→512                            │  W₃: 128→512    │
        ▼  + b₃ , LINEAR  ← no activation          ▼  + b₃ , LINEAR  │
   g̃(x)                (512,)                                (512,) ←┘
        │                                          │        (added)
        │  × bc(x) · out_scale                     │
        ▼    bc = 16·x₁(1−x₁)·x₂(1−x₂)  (a scalar) │
   g(x)                 (512,)                 h(z)          (512,)
        └────────────────────┬─────────────────────┘
                             ▼
                     ⟨ g(x) , h(z) ⟩  =  u(x; z)      one number
```

For a batch of `m` points the spatial track maps `(m, 2) → (m, 512)`, and **that matrix is
the cached table**. The solve then does `table @ h(z)`: `(m,512) @ (512,) → (m,)`.

> **Why the last layer being linear matters.** It means the feature bank's rank can never
> exceed `g_hidden + 1`, whatever `R` says. With `g_hidden=128` or `256`, asking for
> `R=512` silently gave rank 129 or 257 — a bug that cost three rounds before it was
> caught. `g_hidden ≥ 2R` is the fix. A nonlinearity there would lift the cap but destroy
> the linear-in-`h(z)` structure the whole caching trick depends on.

Two details that matter: `bc(x)` is zero on the boundary, so **every** possible output
satisfies the boundary condition exactly, for free. And `h` is **nonlinear**, which is what
makes this a *nonlinear*-manifold ROM rather than a classical linear basis method.

## Why it is built this way

Every ROM faces the same trap. You solve for 16 numbers instead of a million — but to check
whether your 16 numbers are any good, you have to expand them into a real field and test the
physics. That expansion touches the whole grid, and it costs back everything you saved.

The split removes the expansion:

```
   OFFLINE, once                              ONLINE, every solve
   ─────────────                              ───────────────────
   pick m ≈ 256 sample points                 guess z
            │                                     │
            ▼                                     ▼
   evaluate g there  ────▶  TABLE  ─────────▶  TABLE × h(z)
                          (m × 512)                │
                                                   ▼
                                          check the PDE at those points
                                                   │
                                                   ▼
                                          nudge the 16 numbers, repeat
```

Because the sheets never depend on `z`, they are evaluated **once**, into a small table.
After that, testing a guess is one small matrix multiply. **The grid never enters the
solving loop** — it appears only at the very end, when the answer is finally painted onto
the full mesh to look at.

That is the whole reason for the design, and it is why the solve costs roughly the same at
every resolution.

## What the Poisson numbers say

**The cost claim works.** The ROM solve stays at 2–3.5 ms from a 3,800-unknown grid to a
1,000,000-unknown grid, while the iterative classical solver grows from 1.3 ms to 98 ms.
They cross near N=128, and by N=1024 the ROM is ~28× faster. This is the architecture's
central prediction, confirmed over a 256× range of problem size.

**Two honesty notes, both important.**

1. The ROM is faster *at its own accuracy level*, roughly 3e-2. The classical rungs it beats
   are still several times more accurate. This is a Pareto statement, not an equal-error
   win.
2. Poisson here has constant coefficients, so an exact spectral solver exists and beats
   everything — 0.64 ms at machine precision. The ROM's advantage is against **iterative**
   solvers on problems with no fast direct method. Burgers is such a problem; this Poisson
   setup is not, which is exactly why Poisson is the control and not the headline.

**Accuracy is limited by the recipe, not the sheets.** P3 shows the basis can represent
fresh solutions to ~8e-4 — well past what we achieve. P2 shows the trained model reaching
~9e-3. The gap is `h`: the 16-number recipe cannot reach everything its own sheets could
express. (The P2 runs also predate the rank fix — their basis was capped at an effective
rank of 257 rather than the nominal 512, which the later Burgers work corrected.)

That single gap — `h`'s ability to pick good recipes for problems it has not seen — is the
open problem in this project, on both PDEs.
