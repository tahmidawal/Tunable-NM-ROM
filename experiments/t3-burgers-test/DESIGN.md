### 4.1 POD / quadratic-manifold bases — rebuilt, identical recipe, training data only

The parent jobs did not store the bases (only their hashes), so they are **rebuilt in-job** by the parent's code:
128 training trajectories `params_draw(0,128)` solved at the target mesh (`sfit.snapshots`, ntol $10^{-9}$, ltol
$10^{-7}$, every 2nd step, 3328 snapshots); POD = uncentred method of snapshots with the eigenproblem solved for
kmax = 512 as in the parent (`pod_fit_kmax`), rank-16 arm = first 16 modes; quadratic manifold $r=16$ by `sfit.qman_fit`
(centred, ridge grid $\{0,10^{-10},10^{-8},10^{-6},10^{-4},10^{-2},1\}$, 20 % trajectory-split holdout, seed 20260922).
No test case enters any fit. **Reproduction check against the parent's record** (`inputs/dev-reference.json`, frozen
now from the parent's committed summaries and result files, SHA256 recorded there):

- snapshot matrix SHA256 equal to the parent's → bases reproduced exactly (reported);
- otherwise (another GPU model can change last bits): top-16 POD eigenvalues within $10^{-8}$ relative, same QM ridge,
  QM held-out relative error within $10^{-6}$ relative. A failure is reported beside the rows, not worked around.
- POD mode SHA256 (kmax 512) and QM bank SHA256 are compared and reported (equal only if bitwise reproduced).

## 5. Protocol (the parent's, unchanged)

One allocation per mesh. Phase F: all 15 FOM settings + the head arm, quick run then randomised, burn-separated
(0.25 s), synchronised timed panel, 5 repetitions × 64 cases. Phase S: bank-span arm (ρ, then its own 5 × 64 block),
snapshots, fits, POD-16 and QM-16 (twin quick run for the parity gate, then own 5 × 64 block). Phase B: bracket
re-timing of every Phase F subject (2 × 64). GPU ms = median over (case × repetition) of input-resident-on-GPU → six
output fields on GPU, synchronised.

**Table-3 FOM rule (as in the paper's cells):** one FOM setting per cell = the fastest Phase-F-timed setting of the full
15-setting grid whose worst test error is ≤ the worst test error of the NM-ROM accurate row, same job; every row's
speedup = that FOM's GPU ms / the row's GPU ms. If no setting qualifies, no ratio is printed. The per-arm rule of the
parent report is also computed (in `summary.json`), not used for Table 3.

## 6. Gates (a failing gate is reported, never worked around)

The parent's gates, evaluated by `audit_t3.py` (NumPy only): backend gpu / x64 / highest; cohort hash; truth converged;
repetition output identical (field SHA256 of every timed repetition = quick run); ≥ 5 repetitions everywhere; order
effect (within-case paired estimator) with the injected +6 % control; bracket drift ≤ 10 % for the head arm and the
rule-chosen FOMs; grid-arm parity (fields on the stored cases, iterations/stop reasons/errors on all 64 cases) ≤ $10^{-9}$;
QM trajectory-split ridge; errors recomputed from full fields ≤ $10^{-9}$ with the perturbed-field control; checkpoint
unchanged; job complete. Added: every arm's worst case must be among its stored fields (so every worst-error number is
recomputed independently); basis reproduction (§4.1).

**Stored fields (deviation, stated):** full fields for all 64 cases × ~20 arms would be ~260 GB at $2048^2$ on a share
that is 93 % full. Stored: cases 0 and 1 for every arm, plus each arm's own worst case, plus the truth for the union.
Every other (arm, case) keeps its field SHA256 and job-computed error; the audit recomputes errors on the stored pairs.
